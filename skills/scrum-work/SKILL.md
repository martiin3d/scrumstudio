---
name: scrum-work
description: Execute Scrum Studio board tasks in this checkout - start/resume, plan, claim, verify, finish or hand off - with minimal tokens and no repeated work.
---

Self-contained lifecycle. Load another scrum-* skill only for its specific operation.

1. **Start** once per session: `work_start(project, client, actor | identity+name)`. If the context already has a "Scrum Studio board (loaded by hook" block or the supervisor says it claimed the task, skip this discovery call and use what it gives. Find the project with `projects` by checkout folder; reuse your persistent identity. Cache `settings_version`, task versions and `measurement_session`; pass `settings_seen`/`task_seen` so unchanged data is omitted. `should_stop=true` → stop.
2. **Resume first.** `resume` lists your own unfinished tasks with their continuity; `next_work` also returns them first. Continue them (`task_get`, then claim) before planning or starting anything else. Keep recorded checks; redo only what continuity or changed files invalidate.
3. **Plan only new authorized scope** ([scrum-rules](../scrum-rules/SKILL.md)): `task_search` first, then one `task_plan`. A same-title task comes back `existing=true` and nothing is created: continue it rather than creating a copy; if its status is Done the work is already delivered. `differs=[...]` lists what changed between your plan and the registered task (wording, criteria, files): if the scope really changed, refine that task with `task_plan(items=[{id, ...}])`; a mere rewording is the same work. `allow_duplicate=true` only for a deliberately separate outcome. A backlog-only request never authorizes execution.
4. **Start and claim in one call** when you already know the task: `work_start(id, claim=true)` (add `files` only to change the planned set). It applies the same atomic checks as `task_claim` (dependencies, WIP, file conflicts); use `task_claim` only after `claim_deferred` or `claimed=false`, or to claim the next task later in the session. Only `claimed=true` grants the token. Respect WIP, dependencies and other agents' file reservations ([scrum-file-locks](../scrum-file-locks/SKILL.md) only on conflict). Never reuse another worker's identity or recover a lost token with a new one.
   `claimed=false` with `branch_busy` (project git automation on): the checkout still holds uncommitted work of another branch; do not stash, revert or switch branches yourself. Finish or hand off your own task on that branch if it is yours, otherwise call `next_work` again (it already filters by the checkout's branch; `branch_skipped` says how many tasks were held back) or use `exclude_ids=[id]`; the refusal is already recorded on the task. A `git` field on a successful claim (`created`/`switched` branch, or `error`) is informational: the server applies the human-enabled Git policy; report failures without silently switching branches or retrying a publication.
   Before editing, inspect the relevant files and existing edits. `dirty_planned` identifies pre-existing changes, including your own interrupted work; it does not establish authorship. Use an existing diff or `task_changes(id, files=[...])` when needed; do not reread unchanged files or create a mandatory assessment log.
5. **Save progress sparingly:** Stop/quota handoffs and crashes already record the edited files automatically (from git, no model call), so:
   - Small task: no intermediate saves; put `continuity="Done: …; Next: …"` in the call you already make (`work_finish`, or one `task_update` before a deliberate pause).
   - Long task, or right after a costly finding (root cause located, design decision, non-obvious constraint): one `task_update(continuity=…)` with the finding and the next step. One call per real milestone, never per step; it replaces the previous summary.
   - On resume, an `interrupted=true` item lists its `edits`: `task_changes(id)` shows that diff in one call; inspect it before continuing.
6. **Verify proportionally:** `scripts/verify.py --files PATH... --run --reuse`. Evidence = checks actually run.
   Review changes proportionally to risk. Reuse a diff already inspected; request `task_changes` only when it adds missing evidence, especially after an interruption or unexpected edits. Its output enters model context; local diff generation does not make reading it token-free. On `truncated=true`, inspect the relevant subset rather than requesting the same dump. A small mechanical change needs no separate review essay. Record only material findings, remaining risks or continuation information.
7. **Finish:** `work_finish(id, token, evidence, log?)` with an optional concise `log` only for new relevant findings; with git automation on, the response's `git`/`git_push` report the server-side commit and push (or their failure) — relay a failure to the human, never retry git yourself; add `claim_next=true` to claim and load the next task in the same call (its token is in `next.claim`), so chaining costs one call per task; `already_done=true` on a retry means complete, never redo it. Use In Review for pending human approval, Blocked for impediments.
8. **Quota/Stop:** supervised by the bridge in Wakeup runs. Optional Claude hooks check at prompts/response/session boundaries, not during long tool sequences; use safe-boundary checkpoints during long unsupervised work. Otherwise [scrum-usage](../scrum-usage/SKILL.md) at safe boundaries. Stop editing before `agent_checkpoint(action=pause|offline)`; it saves continuity and releases your work.
9. **End:** [scrum-close](../scrum-close/SKILL.md).

Token rules: `next_work`, `task_search` and batch headers are navigation; load `task_get` before editing. `task_changes` is on demand, default 200 diff lines; narrow with `files` rather than raising `max_lines`. Fetch snapshots, history, metrics, costs, notes or attachments only when needed (`pending_ai_notes>0` → `task_get(include_notes=true, notes_content=true)`). No routine chat, Daily, Retrospective or duplicate logs. Rare topics (managed batches, model routing, MCP transport recovery, graph-first code reading): [core guidance](references/core-guidance.md).

Git recovery exception: a task whose category is `Git recovery` authorizes its scoped integration/merge and normal push. Inspect current refs, plan/reserve files before editing, preserve other work and staging, and never force push. Do not repeat the original implementation. Record an external blocker and exit if recovery cannot proceed; do not retry in a loop. Ordinary tasks leave enabled Git automation to the server.

With Git Worktrees mode, the supervisor starts you in the task workspace from claim.git.worktree. Keep the canonical project ID and central board; never register a separate board for the worktree. Edit only the assigned workspace and use relative file plans. On any later claim, honor its worktree path before editing. Other task/context workspaces have independent branches/indexes; central file reservations still apply. Preserve partial edits; workspaces remain available across sessions.

Human-only project_settings(git_cleanup=true|false), default false: after successful integration, queue removal of the local branch and clean managed worktree, executed by the existing supervisor offline checkpoint after CLI exit. No AI turn or polling is added. Remote branches, dirty/ignored files, checked-out unmanaged branches and branches needed as origins are retained. Do not manually delete active or unfinished workspaces. Cleanup skips are reported separately from merge failure and never launch a recovery model.

Before cleanup, native code rechecks the task dependency/context component and defers while any related task is not Done/Cancelled, including newly added work. Deferred candidates are reconsidered at later existing CLI-exit events, without polling or model turns. Prefer Branches for one worker when the canonical checkout can be used safely; Worktrees provides optional isolation for parallel workers or a human checkout. Never migrate active/saved workspaces automatically when worker count changes.
