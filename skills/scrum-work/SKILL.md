---
name: scrum-work
description: Execute Scrum Studio board tasks in this checkout - start/resume, plan, claim, verify, finish or hand off - with minimal tokens and no repeated work.
---

Self-contained lifecycle. Load another scrum-* skill only for its specific operation.

1. **Start** once per session: `work_start(project, client, actor | identity+name)`. If the context already has a "Scrum Studio board (loaded by hook" block or the supervisor says it claimed the task, skip this discovery call and use what it gives. Find the project with `projects` by checkout folder; reuse your persistent identity. Cache `settings_version`, task versions and `measurement_session`; pass `settings_seen`/`task_seen` so unchanged data is omitted. `should_stop=true` → stop.
2. **Resume first.** `resume` lists your own unfinished tasks with their continuity; `next_work` also returns them first. Continue them (`task_get`, then claim) before planning or starting anything else. Keep recorded checks; redo only what continuity or changed files invalidate.
3. **Plan only new authorized scope** ([scrum-rules](../scrum-rules/SKILL.md)): `task_search` first, then one `task_plan`. A same-title task comes back `existing=true`: reuse it, never create a copy; if its status is Done the work is already delivered. `allow_duplicate=true` only for a deliberately separate outcome. A backlog-only request never authorizes execution.
4. **Start and claim in one call** when you already know the task: `work_start(id, claim=true)` (add `files` only to change the planned set). It applies the same atomic checks as `task_claim` (dependencies, WIP, file conflicts); use `task_claim` only after `claim_deferred` or `claimed=false`, or to claim the next task later in the session. Only `claimed=true` grants the token. Respect WIP, dependencies and other agents' file reservations ([scrum-file-locks](../scrum-file-locks/SKILL.md) only on conflict). Never reuse another worker's identity or recover a lost token with a new one.
   `claimed=false` with `branch_busy` (project git automation on): the checkout still holds uncommitted work of another branch; do not stash, revert or switch branches yourself. Finish or hand off your own task on that branch if it is yours, otherwise select other work with `exclude_ids=[id]`; the refusal is already recorded on the task. A `git` field on a successful claim (`created`/`switched` branch, or `error`) is informational: the server owns branches, commits and pushes; the agent never runs `git commit`/`push` for board work.
   **Before editing** read the planned files once and form a short assessment (what the code does, the risk of the change, what you will not touch). `dirty_planned` in the claim result lists planned files that already have uncommitted edits: those are not yours; `task_changes(id, files=[...])` shows them before you build on them. Do not spend a call on this assessment alone; it goes into the first `continuity`/`log` you already send (step 5) as `Before: …`.
5. **Save progress sparingly:** Stop/quota handoffs and crashes already record the edited files automatically (from git, no model call), so:
   - Small task: no intermediate saves; put `continuity="Done: …; Next: …"` in the call you already make (`work_finish`, or one `task_update` before a deliberate pause).
   - Long task, or right after a costly finding (root cause located, design decision, non-obvious constraint): one `task_update(continuity=…)` with the finding and the next step. One call per real milestone, never per step; it replaces the previous summary.
   - On resume, an `interrupted=true` item lists its `edits`: `task_changes(id)` shows that diff in one call; inspect it before continuing.
6. **Verify proportionally:** `scripts/verify.py --files PATH... --run --reuse`. Evidence = checks actually run.
   **Review your own diff once**, before finishing: `task_changes(id)` returns the uncommitted edits of the planned files as a bounded diff (git, no model call) plus `unplanned` files touched outside the plan. Read it and write a 2–4 line opinion: what changed and why, anything risky or left incomplete, and whether `unplanned` edits belong to this task (revert or add them to `files`) or to someone else (leave them). If `truncated=true`, review by file (`files=[subset]`) or open the files; never ask for the whole dump twice. `git=false` (checkout not under git): skip the diff and base the review on the planned files you edited. The opinion is not a second implementation pass: fix only real defects you spot, then record it (step 7) and repeat it in your final answer to the human.
7. **Finish:** `work_finish(id, token, evidence, log="Before: …; After: …")` with the pre-edit assessment and the diff review in `log` (one entry, no separate activity call); with git automation on, the response's `git`/`git_push` report the server-side commit and push (or their failure) — relay a failure to the human, never retry git yourself; add `claim_next=true` to claim and load the next task in the same call (its token is in `next.claim`), so chaining costs one call per task; `already_done=true` on a retry means complete, never redo it. Use In Review for pending human approval, Blocked for impediments.
8. **Quota/Stop:** supervised automatically in Wakeup runs (bridge) and in Claude Code with the optional hooks; otherwise [scrum-usage](../scrum-usage/SKILL.md) at safe boundaries. Stop editing before `agent_checkpoint(action=pause|offline)`; it saves continuity and releases your work.
9. **End:** [scrum-close](../scrum-close/SKILL.md).

Token rules: `next_work`, `task_search` and batch headers are navigation; load `task_get` before editing. `task_changes` is one call per task (resume and/or before finish), default 200 diff lines; narrow with `files` rather than raising `max_lines`. Fetch snapshots, history, metrics, costs, notes or attachments only when needed (`pending_ai_notes>0` → `task_get(include_notes=true, notes_content=true)`). No routine chat, Daily, Retrospective or duplicate logs. Rare topics (managed batches, model routing, MCP transport recovery, graph-first code reading): [core guidance](references/core-guidance.md).
