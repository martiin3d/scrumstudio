---
name: scrum-metrics
description: Inspect Scrum Studio project flow charts or task time-in-state with compact on-demand MCP metrics, distinguishing partial history and calendar time from agent usage.
---

- For a project, use `project_metrics(project,days=30)`; default summary excludes chart series. Use include_series=true only for a requested chart or date-level analysis. days accepts 1..365, counting UTC calendar dates including today.
- Distribution/open counts reflect current state. Done transitions count re-completions; completed_tasks counts distinct tasks with a Done transition in the period. Cancelled is separate and never successful completion.
- Average lead time is creation to the latest Done in the period; cycle time is first In Progress to that Done. Report sample counts. Tasks whose first record is a migration baseline are excluded from these averages because earlier history is unknown. Observed state averages include partial visits clipped to the selected period; do not present them as full lifecycle averages.
- For one task, call task_timing(project,id). It returns cumulative calendar seconds per state, including repeat visits and current residence. history=true adds up to 20 recent visits; before=oldest and limit (max50) paginate. Metadata edits, renewals and task release do not reset state clocks. Done/Cancelled residence also accumulates and can be followed by reopening.
- partial_history=true means tracking began after the task existed. Never invent earlier durations. These metrics measure calendar flow including waiting, not CPU time, agent effort, tokens or financial cost.
- Use metrics when requested or when a specific process question needs evidence, not after every task or in idle polling. Summarize the useful bottleneck and limits briefly. The website's Metrics page offers current distribution, observed state times and daily completion/cancellation flow.

For coordination cost use coordination_metrics(project), also visible under web Metrics. It aggregates local MCP calls, failures, UTF-8 request/response bytes and server elapsed milliseconds by tool. Excludes web requests, model execution and pre-instrumentation history. Stores no arguments, tokens or response contents and is not exported. Tokens are unavailable, not estimated from bytes. Compare equivalent workloads before claiming savings; aggregate timings alone cannot establish an improvement. No routine per-task measurement calls.

work_start returns measurement_session. Include it in later project MCP calls; new sessions get a new ID, reconnects may explicitly reuse it. coordination_metrics(filter_session?,task?) filters measurements; web Metrics shows latest20 sessions and top50 tasks. Untagged calls stay unattributed, no guessed attribution; task IDs are local. start_mode is startup eligibility, not proof of all operations using that mode. Compare equivalent workloads; bytes/time are not provider tokens, and legacy totals may predate scoped instrumentation.

Optional cost: task_create/task_update accept estimated_tokens and estimated_quota_percent (null clears). task_update/work_finish accept usage_report={run_id,source,input_tokens,output_tokens}. Supply only actual client telemetry attributable to this task and agent; use stable task-specific run IDs, cumulative monotonic counts and the same source. Input includes cached tokens; never add cache again. Retries replace the same agent/run snapshot, separate agents/runs accumulate. Do not copy whole-chat counts to several tasks, guess missing usage, convert bytes into tokens, or allocate shared account quota. Reports survive Done/Cancelled; missing data stays unavailable and reported coverage may be partial. Reuse existing completion/update calls; no model estimation or quota polling solely for cost.

Cost is opt-in: task_get(include_cost=true) returns estimates and reported totals. Default task_get, next_work, work_start and snapshot omit cost. Versions identify the selected view; keep separate cached versions for cost/non-cost reads. Routine task execution should not load this skill unless a metric or existing telemetry needs handling. For repeatable isolated payload comparisons run scripts/benchmark_coordination.py; it measures response bytes, not tokens/quota, and uses disposable fixtures.

Actual CLI counters are optional on-demand data: coordination_metrics(project,include_cli_usage=true) adds cli_usage with execution count, known-run coverage and reported input/output/cache/reasoning counters. It never adds these to startup/task context. The supervisor reads existing terminal CLI log events and attaches cli_usage_report to its existing checkpoint, with a unique run ID. Duplicate callbacks count once. Batch execution counters stay shared at project level, not copied or divided into task costs. Codex coverage is the terminal completed turn, Claude the terminal run summary; missing counters/failed runs remain unknown, never zero. Cache/reasoning counters are subsets of provider totals; do not add them twice or convert them into account quota/money. No extra provider/model request is used for measurement.
